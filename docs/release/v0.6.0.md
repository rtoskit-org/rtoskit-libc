rtoskit-libc 0.6.0 adds a third prebuilt flavour, the `fast` build, a faster maths library with a looser accuracy contract. It also fixes accuracy defects in the strict maths library, which the `release` and `speed` builds use. The public headers and the ABI are the same as in 0.5.3, so a program built against 0.5.x links unchanged.

## New: the `fast` build

`fast` is the `speed` build with a different maths library. It is faster and less accurate, and it is accurate to nearest only. Everything outside maths is the same as in `speed`.

- **Accuracy:**
  - below 1 ulp, rounding to nearest; 1.5 ulp for `tan`, `tanf`, the hyperbolic functions and `erf`;
  - `sqrt` and `hypot` stay correctly rounded;
  - `erfc`, `lgamma` and `tgamma` below 1 ulp, and `lgamma` within 2^-60 absolutely next to its zeros;
  - the float complex functions keep the strict contract.

  The functions aim at 0.55 ulp. On the Cortex-M4F and M33 the float functions aim at 0.9 ulp, and on the Cortex-M7 so do `asin`, `acos` and `atan`.
- **Directed rounding:** other rounding modes keep each result's sign, not its accuracy. Use `release` or `speed` where code changes the rounding mode.
- **Speed:** maths takes a third to a nineteenth of the `release` build's instructions, depending on the core: a sixth on the Cortex-M4F. On every core it is at or below Arm Optimized Routines' count for each function AOR implements. Against picolibc it is at or below on every function on every core except four on the Cortex-M7: `atan` (1.12×), `asin` (1.07×), `acos` (1.04×) and `log1p` (1.004×).
- **Size:** smaller than `speed` for float-only programs on most cores, and larger where double maths come in. A program that mixes float and double maths grows by 3–4 % on the Cortex-M0 and M4F, and by 29 % on the Cortex-M7.

The README's new section *Choosing release, speed or fast* compares the three builds' contracts, code sizes and instruction counts per core, and says which suits which application. A program links one build; it cannot mix them. The contract and the measurements are in `docs/research/fast-math.md` and the `libm-fast-*.md` notes.

## Fixed in the strict maths library (`release` and `speed`)

These change results, always towards the correctly rounded one, in every build type that uses the strict files:

- **`pow`:** ±1 to an integer power beyond 2^20 is exact again. (−1)^y lost its sign there, and, rounding downward, 1's last bit.
- **`atanf`** on the Cortex-M0, M0+, M4F and M33: correctly rounded again just below 1/16, where it was 1.27 ulp off.
- **`log1p`:** no longer raises a spurious underflow for large arguments.
- **`sin` and `cos`:** new cores, below 0.53 ulp over the whole range (they reached 0.59–0.61 ulp, mostly beyond 2^20).
- **`erf`:** below 2^-28 it now keeps the second term, taking it from 0.53 to 0.50 ulp.
- **`lgamma`:**
  - below 0.53 ulp on (0, 3), where it reached 0.68 ulp;
  - within 2^-60 absolutely next to its negative zeros, where it was up to 2^-49 off (results there are tiny, so this was up to 10^13 ulp);
  - lgamma(−2.5) correctly rounded.

These fixes add about 0.7–1.1 KB to `lgamma` and under 80 bytes to `erf`, and only to programs that call them; `pow` and `atanf` got smaller. `tgamma` takes about 2–3 % more instructions, through its exp(lgamma) form.

## Downloads

One archive per architecture, `rtoskit-libc-0.6.0-<arch>.tar.xz`, now holding three builds, each in its own directory with `include/` and `lib/`:

- `release/`: the size build;
- `speed/`: the speed build;
- `fast/`: new in 0.6.0.

Each archive comes with `SHA256SUMS` and a build-provenance attestation:

```sh
gh attestation verify rtoskit-libc-0.6.0-armv7e-m.tar.xz --repo rtoskit-org/rtoskit-libc
```

The architectures are those of 0.5.0: `armv6-m`, `armv6s-m`, `armv7-m`, `armv7e-m`, `armv7e-m-dp`, `armv8-m.main` and `x86_64` (the test host). The toolchain floor is unchanged: GCC 14 or newer, and arm-none-eabi GCC 16.2 as the tested Arm compiler.
