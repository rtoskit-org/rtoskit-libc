# Making a release

A release is a signed tag `vX.Y.Z` on `main`, and a GitHub release that holds one prebuilt archive per
architecture. Versions follow semantic versioning; while the major number is 0, a minor release may break
the ABI or the RTOS interface (PLAN D158).

## What the release workflow does

Pushing a tag that matches `vX.Y.Z` runs `.github/workflows/release.yml`:

1. On every architecture, the same gate as a pull request: `make check` in all four build types and, on
   Arm, the size gates. A failure stops the release; nothing is published.
2. `tools/scripts/release-package` installs the headers and archives of the `release` and `speed` builds
   (`make library`) into `rtoskit-libc-X.Y.Z-<arch>.tar.xz`, with `LICENSE`, `README.md` and `VERSION`.
   The `fast` build type joins the archives only once phase 11 meets its exit criterion (P11.06, D163).
3. It writes `SHA256SUMS` and a signed build-provenance attestation for each archive
   (`gh attestation verify <archive> --repo rtoskit-org/rtoskit-libc`). Archives of 0.5.0 to 0.5.2 were
   attested before the repository moved to rtoskit-org; verify them with `--repo sgstreet/rtoskit-libc`.
4. It creates a **draft** release with the archives and the notes. A `0.x` or `-rc` version is marked as a
   pre-release.

A draft is visible only to people with write access. Nothing is public until you publish it.

## How the release notes are made

The notes have two parts, in this order:

1. **The highlights**, written by hand in `docs/release/vX.Y.Z.md` and committed before the tag. They say
   what the release is for, what is new, the supported architectures and anything a user must act on (an
   ABI change, a toolchain requirement). The workflow refuses a tag without this file.
2. **The change list**, generated by GitHub: every pull request merged since the previous release, with
   its author and a link, grouped by label as `.github/release.yml` sets out (`breaking`, `enhancement`,
   `bug`, `performance`, `documentation`, everything else under "Other changes"; `skip-release-notes`
   leaves one out). The first release has no previous release to start from, so its notes are the hand-written part alone.

You can edit both parts in the draft before you publish it.

## Releasing

1. Write `docs/release/vX.Y.Z.md`, open a pull request with it and merge it once CI is green.
2. Create a signed, annotated tag on that commit of `main` and push it. The signature is your sign-off on
   the code being released:

   ```sh
   git fetch origin main
   git tag -s vX.Y.Z -m "rtoskit-libc vX.Y.Z" origin/main
   git push origin vX.Y.Z
   ```

   `-s` signs with your GPG key, or with your SSH key after `git config gpg.format ssh` and
   `git config user.signingkey ~/.ssh/<key>.pub`. Add the same key to GitHub (Settings, SSH and GPG keys,
   as a signing key) and the tag shows as **Verified**. Check it locally with `git tag -v vX.Y.Z`.
3. Watch the `release` workflow in the Actions tab (about 10 minutes).
4. Review the draft under Releases: the notes, the eight files (seven archives and `SHA256SUMS`), and that
   the tag shows as Verified. Then press **Publish release**. Publishing is your sign-off on the release
   itself.

If the workflow fails, fix the cause on `main` and move the tag only if the release was never published
(`git push origin :refs/tags/vX.Y.Z`, then tag again). To rebuild the draft for a tag, delete the draft and
run the workflow from the Actions tab with the tag name (`workflow_dispatch`). Never move a published tag:
make a new patch release instead.

## Protecting releases (repository settings, once)

- **Rulesets, tags:** a tag ruleset on `v*` that restricts creation, update and deletion to administrators
  keeps anyone else from starting a release or moving a published tag.
- **Releases, immutable releases:** once enabled, a published release's assets and tag cannot change.
